# Mapping a project, before anything is graded

This is the cheap first pass, and for most people it is the whole product. It answers one question —
**is anything here in nobody's care?** — and it does it without grading a single thing.

Grading comes later, one part at a time, only when someone is about to work on that part. That is
`ladder-grade`, and it is expensive: measured on the first project, roughly 380,000 tokens per part
per grading. This mapping is roughly one run of that, for the whole repo, and it is what makes the
expensive step optional instead of compulsory.

**Do not grade anything here.** Every letter stays `null`. A map with invented grades is worse than
no map, because everything downstream trusts the letters.

## What you produce

**Copy every file out of `template/` into `docs/quality/`** (or wherever the project keeps
documents), then edit two of them:

- **`ladder.js`** — the only real work. The template carries one example row: copy its shape
  EXACTLY for every part, every field present even when empty. A missing `feels`/`guts`/`field`
  reads as "never graded" and costs nothing; a missing `parts` is different, and the card says
  **watches no files** — the row exists, its files sit in the census as if unclaimed, and only that
  chip tells anyone why.
- **`history.js`** — fill in the date on its single starting entry. Everything the front page says
  about MOVEMENT is derived from this file and nothing else, so its shape matters: `kind` is one of
  `mapped` · `graded` · `regraded` · **`rechecked`** (re-verified and the letters held — the payoff
  event, and the one most easily forgotten) · `fixed` · `expected` · `described`, and a `fixed` entry
  may carry `clears: [indexes into that row's next.needs]` as a CLAIM about what it addressed. The
  file is append-only: position is time, which is how the board knows a repair has not been
  re-checked yet without recording anything extra.
- **`explain.js`** — copy unchanged, and leave it EMPTY. It holds the plain-words description of
  each part, and only a real check may write one: a description written by a pass that skims is the
  one thing on this board nobody verified, and the board's whole claim is that everything on it is
  either computed or earned. A part with no entry says so on its own page, which is true and free.
- **`index.html`**, **`refresh.mjs`**, **`roadmap.js`** — copy unchanged. The page opens from disk
  with no server and no build, and names itself from `ladder.project`. `roadmap.js` ships empty on
  purpose: it fills in only once a project has been graded, and shipping it empty is what stops a
  correct first day from throwing a missing-file error.
- **`questions.js`**, **`questions.mjs`**, **`serve.mjs`**, **`questions.test.mjs`** — copy unchanged.
  These are the "Your call" tab: the decisions an agent made on its own and the ones it could not make
  for the owner. `questions.js` ships empty, and the tab hides itself until there is something in it.
  `serve.mjs` is the only part of this board that needs a server, and it is needed only to ANSWER —
  `node docs/quality/serve.mjs`, loopback only, no dependencies.

Then run `node docs/quality/refresh.mjs`, open the page, and LOOK at it before reporting.

## Updating a board that already exists

**A board is copied, so it never hears about an improvement again.** Measured on the second project
this shipped to: its `index.html` was **854 lines behind**, missing four whole sections, and nothing
on the page or in this skill would ever have said so — it was found by running a diff by hand.

The page therefore prints its own age under the title (`board 2026-08-12`), from `BOARD_VERSION` near
the top of its script. Compare that against `template/index.html` — one `grep` on each. **A board
with no `BOARD_VERSION` at all predates the stamp and is therefore older than every stamped one**,
which is the state every board shipped before today is in. If the template is newer:

- **Replace** `index.html`, `refresh.mjs`, `roadmap.js`, `questions.mjs`, `serve.mjs`,
  `questions.test.mjs`. These are the board itself and are identical in every project — `roadmap.js`
  only if the project has never been graded, since a graded one holds real themes. A board with no
  `questions.js` at all gets the empty one too; one that already has questions keeps it.
- **Never touch** `ladder.js`, `history.js`, `explain.js`, `questions.js`. Those are the project's own record, one of
  them append-only, and none of them is what went out of date. `staleness.js` is generated by
  `refresh.mjs`, so it looks after itself.
- Then re-run `refresh.mjs` and **open the page**. Old data is meant to keep working — every field a
  newer board adds hides itself when absent, and that was verified by rendering one project's board
  against another project's ungraded, group-less, verdict-less data — but "meant to" is not a check,
  and the one bug that pass found (an empty column still drawing its rule across a third of the
  masthead) only appeared on the older data.

Do this as its own act, announced, never quietly folded into a grading session: replacing the page
someone reads is a change they should hear about, and it is the one edit here that touches no data
and can therefore be undone with a single copy.

## How to draw the parts

**A part is a promise to a person, not a folder.** "Playing music — click a song and it plays fast,
at the right quality, with nobody ever served someone else's stream" is a part. "The services
directory" is not. The promise is what a grade is later measured against, so a vague one makes every
future grade vague: write what a person would notice if it broke.

Getting there:

1. **Read the project's own words first** — its readme, its architecture notes, its changelog. Where
   they exist they have usually already named the parts; do not invent a taxonomy over the owner's.
2. **Then walk the code** and place every source file into exactly one part where you can. Shared
   files legitimately appear in several parts; that is not a mistake, and later it is what reveals
   that one defect spans three promises.
3. **Aim for 8–20 parts.** Fewer and a part is too big to grade in one session; more and the board
   stops being readable at a glance. At that count the board reads better if each row carries a
   `group` — one of `finding music` · `playing it` · `keeping it` · `sharing it` · `running it`, the thing the
   PERSON is doing. It is optional and cosmetic; leave it off when a project has no natural runs.
   **Never group by frontend/backend**: measured on the first project, 13 of the 14 rows listed both
   web and server files, so that split cuts almost every row in half — and it is the folder taxonomy
   a part is defined in opposition to.
4. **Include the unglamorous ones** — accounts, backups, the admin surface, the build. On the first
   project the backup part turned out to hold the only defect that could lose data permanently.

**When the project has no architecture notes**, step 1 is empty and step 2 is the whole job — and
both projects this skill has run on happened to be thoroughly documented, so it has never actually
been tested there. Without prose to lean on, take the promises from what the project DOES rather
than from where its files sit: **write down** every entry point a person can reach — screens,
routes, commands, jobs, scheduled work, public functions — and skim the bug reports and commit
messages, which are already written in promise language, because "X didn't work" names a promise by
breaking it. **A part is something that can be reported broken**; if you cannot imagine the report,
you are looking at a folder. You are done with that list when every item on it either lands in
exactly one row's promise or is written into the report as deliberately left out. Count both sides
and say the two numbers — a list you never reconciled is a list you only read.

**A part ten times the size of its neighbours is a question, not a verdict**, and the obvious test
is the wrong one: "would a person notice two different things breaking in here" is true of every
screen ever built, so it always answers *split* and tells you nothing. Ask instead whether you can
**write two promise sentences and hand every file in the part to exactly one of them.** If you can,
they were two rows all along and the directory was hiding it. If every division you try leaves the
same sentence true on both halves — one system, one contract, a hundred files — keep it whole, and
write the size into its `notes`, because its first grade will only reach part of it and will have to
say so. Splitting one promise to make the board look even is the same lie as inventing a part to
make the census look smaller.

## The census is the point

`refresh.mjs` reports every tracked source file that no part claims, with the biggest first, and the
board prints it in red beside the reassuring sentence. Expect the number to be embarrassing: the
first project measured **46 of 136 files, 7,430 lines** in nobody's care after a full manual mapping
— including its largest file and its login gate.

Two rules about it:

- **Do not fix the number by inventing parts.** A part with a promise nobody would miss is a lie
  that also makes the census look better. Leave the file uncovered and say so.
- **A file nobody watches voids every promise above it.** A grade cannot go stale from a file no part
  claims, so the census is not a nice extra — it is the honesty of everything else.

## What NOT to do here

- **Do not grade.** Not "obviously fine", not "clearly rough". Letters stay `null`.
- **Do not explain.** You will finish this knowing how much of the project works, and writing it into
  `explain.js` is the most tempting thing here — it is also the only claim on the board that no
  check stands behind. The part pages say the description arrives with the first check, and they
  should keep saying it.
- **Do not set targets.** An expectation before the map is a guess about cost.
- **Do not write a roadmap.** It is derived from grades, and there are none.
- **Do not fix anything you notice.** Write it in the part's `notes`, dated, and move on. If it is
  actively dangerous — data loss, a leaked credential — stop and tell the owner instead.

## Reporting back

Give the owner, in plain words: how many parts, what the biggest ones are, how much code is in
nobody's care and which files those are, and the one sentence that matters — **nothing has been
graded, and here is what grading one part would cost**. Offer to grade the part they most care about
rather than proposing to grade everything: on the first project, grading everything cost 4.6 million
tokens, and the map alone already answered the question they actually asked.
